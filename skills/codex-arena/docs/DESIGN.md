# Codex Arena — проект архитектуры

Дата: 2026-10-16. Статус: архитектура согласована; реализована v0.1. Детали фактического поведения и ограничения: [README](../README.md).

## Назначение и варианты

Одноразовый глубокий аудит и улучшение локального Git-проекта с проверяемым результатом в отдельной ветке. Рекомендуется самостоятельный Python CLI, управляющий процессами `codex exec`. Альтернативы: skill с ручным запуском каждого задания (проще, но хуже автономность и восстановление); прямой API/SDK (больше контроля, но иной биллинг и ненужная зависимость первой версии). Claude-специфичные Agent calls не переносим. Из оригинала используем идею разнообразных стратегий, сетки и взаимной критики; реализацию пишем самостоятельно.

## Команды

`codex-arena plan PATH --agents 32`: без вызовов модели показывает стадии, число вызовов, конфигурацию проверок и ориентиры бюджета.

`codex-arena audit PATH`: 32 независимых аудита, объединение находок, турнир планов до восьми финалистов; исходники не изменяются. Результат пригоден для продолжения через run.

`codex-arena run PATH --agents 32`: полный процесс; если существует совместимый завершённый audit, продолжает его. Несовместимая база или конфигурация требуют нового run-id.

`codex-arena resume PATH --run ID`: продолжает задания сохранённого запуска. При нескольких запусках ID обязателен; никакого выбора произвольного последнего.

`codex-arena status PATH --run ID`, `codex-arena report PATH --run ID`: без вызовов модели.

## До старта

Цель — корень Git-репозитория с существующим HEAD. Фиксируются абсолютный путь, Git common-dir, base SHA, конфигурация, версии CLI и модели. Первая версия требует чистого рабочего дерева: несохранённые изменения не прячет и не коммитит. Исходный checkout и main не меняются. Все команды проекта, включая baseline, исполняются в отдельных worktrees. Зафиксировать base SHA можно от текущей ветки, а не обязательно main.

Проверки задаются явно в TOML: setup, tests, lint, typecheck, build, smoke и benchmarks. Каждая команда — argv, cwd внутри worktree, timeout, допустимые коды возврата и, при необходимости, разбор структурированного результата. Smoke должен иметь ограниченный срок жизни и гарантированное завершение дерева процессов. Автообнаружение предлагает команды, но не объявляет пропущенную проверку успешной. Отсутствие конфигурации обязательных проверок останавливает переход к исправлениям с конкретной диагностикой.

## Стадии и сетка

1. Baseline: неизменяемый checkout base SHA, проверки, идентификаторы упавших тестов, длительности, среда и логи.
2. 32 независимых read-only аудитора: 16 направлений × две разные стратегии. Архитектура, бизнес-логика, edge cases, состояние/конкурентность, API, данные/миграции, безопасность, зависимости, тесты, производительность, типизация, обработка ошибок, интерфейс/доступность, сопровождаемость, сборка/эксплуатация, документация. Неприменимые направления перераспределяются по стеку с записью решения. Все читают одинаковую базу и задачу; до завершения не видят выводы других.
3. Общий реестр: исходные находки сохраняются, дубликаты связываются без удаления доказательств. Поля: ID, источник, категория, severity, файл/строка, сценарий воспроизведения, ожидаемое/фактическое поведение, доказательство, уверенность, статус. Модельное предположение не становится подтверждённой проблемой автоматически.
4. Раунды 32→16 и 16→8: два attack, два defend, один judge на матч. Здесь сравниваются доказательства и планы исправления, а не число найденных пунктов. Нужные воспроизводящие проверки выполняет проверяющий runner. Судья не может исключить подтверждённую находку из общего реестра. На этапе audit создаются восемь планов с доступом к общему реестру.
5. Восемь кандидатов: каждый получает отдельную ветку `arena/<run>/cNN` и worktree от одной базы; реализует целостный план с учётом общего реестра. Создание кандидатов — восемь дополнительных вызовов.
6. Раунды 8→4→2→1: attack читает замороженные снимки обоих кандидатов; defend меняет только собственный worktree. После защиты runner фиксирует commit и повторяет проверки. Judge получает результаты именно этих SHA. Победитель наследует свою ветку; полезные исправления проигравшего заносятся в очередь переноса и при следующей защите переносятся только с повторной проверкой. Автоматического merge проигравших нет.
7. Независимый финальный аудит read-only; при требуемых исправлениях — отдельное задание защиты и повторные проверки в рамках бюджета. Статус ready появляется только после прохождения обязательных gates. Иначе результат incomplete/needs-review с веткой и причинами.

Базовый полный прогон: 32 + 31×5 + 8 + 1 = 196 модельных заданий плюс отдельная консолидация находок (1): 197. Это не обещание меньшего числа вызовов: экономия ожидается за счёт меньшего объёма работы до восьми кандидатов. Повторные попытки и финальные исправления учитываются отдельно. Audit до восьми планов: 32 + 24×5 + 1 = 153 задания. Допустима будущая сокращённая селекция, но первая версия сохраняет полную attack/defend/judge-схему.

## Выбор победителя

Объективные gates имеют приоритет над баллами модели: выполнены обязательные проверки; нет новых падений относительно baseline; нет удаления/ослабления проверок ради победы; нет недопустимых изменений; нет подтверждённой критической регрессии. Удаление тестов не всегда запрещено, но требует доказанного обоснования и отдельной проверки. Старое падение отслеживается по идентичности теста, одного количества недостаточно. Для инструментов без структурированных результатов runner может доказать только код возврата; ограничение явно отражается в отчёте.

Неприменимо, пропущено, ошибка среды и успешно — разные состояния. Если оба кандидата провалили gates, матч не выбирает победителя: ограниченная попытка исправления или остановка needs-review. Judge выдаёт аргументы и оценки, арифметику и допустимость вычисляет Python. Среди допустимых: устранение подтверждённых проблем 35%, корректность/robustness 30%, качество проверок 20%, сопровождаемость diff 15%. Размер diff — сигнал для обзора, а не самостоятельная цель минимизации. Benchmarks сравниваются при одинаковой среде, с повторениями и заданным порогом шума; без них ускорение не объявляется доказанным.

## Codex adapter и модели

Используются `codex exec --json --output-schema ... -o ...`, явные cwd, model и model_reasoning_effort. Prompt передаётся через stdin, без интерполяции shell. Проверяются capabilities установленной версии CLI. Authentication используется существующая CLI; миграции на платный API по умолчанию нет. Название Sol из интерфейса не считается автоматически валидным CLI model-id: требуется doctor/config и минимальная явно запрошенная проверка доступа, без молчаливого fallback.

Расписание: 32/16 medium, 8 medium для реализации и high для спорных ревью, 4/2 high, финальный аудит high. Модель настраиваемая; доступность проверяется отдельно. 32 — число участников, не одновременных процессов. По умолчанию concurrency=2, проверки тяжёлых проектов сериализуются; можно повысить явно.

Read-only роли работают в read-only sandbox; редакторы — workspace-write в собственном worktree. Worktree не является полноценной защитой от произвольных внешних действий: учитываются доступы CLI/MCP/hooks, не используется bypass sandbox. Запрещены push, merge main, публикация, изменение пользовательских настроек. Для строго враждебного репозитория понадобится внешний контейнер; это отдельный backend, не обещание первой версии.

## Состояние и восстановление

Состояние хранится вне целевого checkout в пользовательском state-dir, каталог определяется Git common-dir + run-id. SQLite с транзакциями и блокировкой одного оркестратора; prompts, JSONL, stderr, ответы, проверки и патчи — отдельные файлы с хешами. Сущности: runs, candidates, findings, matches, jobs, attempts, checks, usage. Job ID стабилен: run/stage/round/match/role/candidate. Статусы pending/running/succeeded/failed/interrupted; завершение принимается только после проверки схемы, артефактов и SHA.

Результат сначала пишется во временный файл, атомарно переименовывается, затем принимается транзакцией. После сбоя между записью и транзакцией resume импортирует уже готовый валидный артефакт. Журнал содержит session-id и PID/идентичность процесса; живое задание нельзя запускать повторно. Для потерянного ответа неопределённость сохраняется: автоматическая гарантия exactly-once невозможна. Если ответ восстановим из JSONL/сессии — используется он; иначе задание interrupted, требуется явный retry. Успешные задания не повторяются.

Git-операции тоже имеют intent/result: при аварии resume сверяет существующие ветки, worktrees и SHA. Перед повтором оборванного редактора сохраняются diff и untracked; не происходит слепого reset. Внешние изменения кандидата блокируют продолжение до разрешения конфликта. Изменение исходной ветки не меняет зафиксированную базу запуска.

## Бюджет и остановка

Предварительные 5–10/8–12/15/17 млн — пользовательские ориентиры, не измеренный прогноз и не официальный лимит подписки. Учёт usage по каждому вызову: input (включая cached), cached отдельно, output; reasoning не прибавляется повторно без подтверждённой семантики события. Отсутствующий usage остаётся unknown. Raw usage не преобразуется в остаток окна подписки.

Целевой диапазон 8–12 млн, мягкая остановка перед новым заданием на 15 млн, emergency 17 млн. Перед dispatch резервируется оценка задания и всех текущих вызовов. Это ограничения планирования, а не точная гарантия: usage может приходить только после turn и один вызов может превысить остаток. При unknown usage новые вызовы останавливаются до reconciliation. Отдельные ограничения: wall time, число попыток, максимальная параллельность. Сигнал остановки и quota/rate-limit переводят запуск в paused с сохранением состояния, без бесконечных retry. Для жёсткого финансового потолка нужен backend с доступным серверным ограничением.

## Результат

Отдельная победившая ветка и SHA, diff от base SHA, отчёт Markdown/JSON, реестр найдено/подтверждено/исправлено/не решено, таблица baseline/final для проверок и регрессий, benchmarks, usage (включая unknown), принятые компромиссы и журнал матчей. Исправлено считается по доказательству проверки, а не по заявлению редактора. Автоматического merge и удаления worktrees нет.

## Проверка реализации

Сначала fake Codex executable и временные Git-репозитории: полная сетка 32, audit→run, защита main, обе стороны провалили gates, ties, baseline failures, schema errors, timeout, quota, сбой между файлом и commit состояния, оборванная защита с dirty worktree, блокировка второго оркестратора, сохранение usage и бюджетные границы. Затем небольшой реальный pilot на отдельном тестовом репозитории по отдельной команде пользователя; полный прогон не запускается при создании инструмента.

## Уточнения реализации v0.1

- Существующие tests/config защищены консервативно; добавлять обычные тесты можно. Пользовательские protected_paths дополняют базовый список.
- Все обязательные проверки должны пройти полностью; автоматического waiver для старых baseline failures нет. Идентификаторы отдельных тестов пока не извлекаются.
- Финальный blocker или оба недопустимых кандидата останавливают турнир needs-review. Автоматические repair rounds не реализованы.
- Подтверждение исправлений — независимый финальный модельный обзор с evidence плюс внешние gates; автоматического исполнения каждого reproducer нет.
- Benchmark runner сохраняет логи и длительности внешней команды; статистику и пороги регрессии должна обеспечивать сама команда.
- Нет автоматического перераспределения аудиторских ролей по стеку. Полное расписание — 197 заданий, параллельность по умолчанию 2.
- После явного --retry-interrupted незавершённый editor tree сохраняется в recovery-ветку, затем возвращается к checkpoint. Игнорируемые файлы не архивируются.
- После неизвестного usage нужно явное reconcile-usage по подтверждённым данным, до этого новые задания не запускаются.
- Реальная модельная интеграция и AI Factory ещё не прогонялись; тесты используют подмену исполняемого файла Codex на границе с моделью.
