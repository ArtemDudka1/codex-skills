# Codex Arena

Универсальный локальный CLI: 32 независимых аудита → турнир планов до 8 кандидатов → исправления в отдельных Git worktrees → взаимная критика и проверка → отдельная итоговая ветка.

Инструмент написан заново на Python. Идея турнира взята из [Jakeschincariol/arena-skill](https://github.com/Jakeschincariol/arena-skill), MIT. Claude Agent tool не используется. Основа интеграции — [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

## Установка

Нужны macOS/Linux, Python 3.11+, Git и установленный, авторизованный Codex CLI с `exec --json --output-schema -o --sandbox`. Windows без WSL не поддерживается: используются flock, ps и группы процессов POSIX.

Из папки инструмента:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install .
.venv/bin/codex-arena --help
```

Можно без установки: `./bin/codex-arena ...` или из этой папки `python3 -m codex_arena ...`. Исполняемый файл `bin/codex-arena` можно добавить в свой PATH; сам инструмент пользовательские настройки PATH не меняет.

Профиль и файл задачи храните **вне целевого checkout**, чтобы его начальное состояние оставалось чистым. Примеры `examples/python.toml` и `examples/web-app.toml` — шаблоны: команды должны существовать в конкретном проекте. Инструмент не устанавливает ruff/mypy/npm и не придумывает отсутствующие проверки.

## Перед первым запуском

1. Выберите точный `model` ID, поддерживаемый вашим CLI/аккаунтом. В примерах указан `gpt-6.1-sol`, доступность здесь не проверялась. Название модели в интерфейсе приложения не гарантирует совпадение с CLI ID. Молчаливой подмены нет.
2. Укажите setup и независимые tests/lint/typecheck/build/browser/benchmark-команды, применимые к проекту. Обязательные проверки — `required = true`. Необязательная проверка тоже запускается и видна в отчёте; её провал не дисквалифицирует кандидата. Неприменимую проверку не добавляйте: отсутствие не означает успех.
3. Целевой репозиторий должен иметь commit и чистый checkout. Сохраните нужное содержимое перед запуском. Arena не делает stash, не создаёт commit ваших исходных изменений и не инициализирует целевой Git автоматически.
4. Настройте `.gitignore` проекта для зависимостей, сборки и тестовых артефактов. Setup/проверки, меняющие исходники или создающие неигнорируемые файлы, остановят запуск. Для Python runner отключает запись bytecode.

```sh
codex-arena doctor /path/to/project --config /path/to/profile.toml
codex-arena plan /path/to/project --agents 32 --config /path/to/profile.toml
codex-arena audit /path/to/project --agents 32 --config /path/to/profile.toml --task-file /path/to/task.md
codex-arena run /path/to/project
codex-arena resume /path/to/project
codex-arena status /path/to/project
codex-arena report /path/to/project --json
```

`doctor` проверяет установленный интерфейс CLI, но не вызывает модель и не подтверждает доступ к ней. `plan` тоже бесплатен относительно модели. `audit`, `run` и `resume` **запускают реальные модельные задания и расходуют ваш лимит**. CLI использует текущую авторизацию Codex; он не переключает вас на API-биллинг.

`audit` заканчивается на восьми планах (для 2/4/8 участников — после независимых аудитов и консолидации). `run` продолжает найденный запуск; повторно не оплачивает уже сохранённые задания. `resume` продолжает сохранённый режим: для audit снова остановится после аудита. `--new` создаёт независимый запуск. При нескольких запусках укажите `--run ID`; случайный «последний» не выбирается.

## Что происходит внутри

- Один base SHA на весь запуск. Исходный checkout остаётся вне рабочей области редакторов. Даже baseline/setup/проверки работают в отдельном worktree.
- 16 направлений × 2 стратегии: архитектура, логика, крайние случаи, состояние/конкурентность, API, данные, безопасность, зависимости, тесты, производительность, типы, ошибки, интерфейс/доступность, качество кода, эксплуатация, документация. Для 2/4/8/16 участников используется соответствующее число ролей.
- Первый аудит независимый; затем все исходные находки сохраняются с ID. Дубликаты группируются, а не стираются. Находки защиты добавляются, если их содержание новое.
- В матче два attack, две защиты и один judge. До восьми кандидатов защита меняет план, после — собственный worktree.
- Реализацию получают восемь кандидатов; они видят общий реестр, включая находки выбывших аудиторов. В защите видны атака и работа соперника; автоматического merge чужих исправлений нет.
- Судья выдаёт оценки A/B, Python считает итог: покрытие 35%, корректность 30%, проверяемость 20%, сопровождаемость 15%. При равенстве выигрывает меньший ID. Объективные gates имеют приоритет. Если оба провалили их, результат `needs-review`, победителя нет.
- Все обязательные проверки должны пройти. В первой версии нет разрешения сохранять старые падения baseline: это строже сравнения количества регрессий и не требует доверять неполным идентификаторам тестов.
- Новые обычные регрессионные тесты допустимы. Изменения существующих тестов, конфигураций и скриптов проверки ведут к ручному рассмотрению. Дополнительные зависимости проверок нужно указать в `protected_paths`. Защита не является математическим доказательством отсутствия обходов.
- Финальный независимый аудит читает diff, после него ещё раз выполняются проверки. Финальный аудитор не редактирует. При блокирующих проблемах ветка остаётся на рассмотрение; автоматический цикл финальных исправлений пока отсутствует.

Базовый полный прогон 32 участников: **197 модельных заданий** = 32 + 31×5 + 8 реализаций + консолидация + финальный аудит. Audit до восьми — 153. Повторные попытки считаются отдельно. Одновременно по умолчанию два вызова; проверки кандидатов идут последовательно. Создание/защита планов medium, реализация medium, ревью/защита кода и финальный аудит high. Расписание сейчас фиксировано в `Engine.context`.

## Состояние, бюджет и восстановление

По умолчанию: `$XDG_STATE_HOME/codex-arena/<repo-hash>/<run-id>` или `~/.local/state/codex-arena/...`. `--state-dir` меняет корень и должен повторяться во всех командах. Он обязан находиться вне целевого checkout. В каталоге: SQLite ledger, prompts, JSON schemas, JSONL событий, stderr, response envelopes, worktrees, проверки, `report.md`, `report.json`, `final.diff`. Не удаляйте каталог между окнами Codex. Копирование одного SQLite без worktrees и artifacts недостаточно.

Завершённые ответы валидируются и восстанавливаются по устойчивому ID задания. Сохраняются хеши ответов, session ID и PID со временем рождения процесса. Параллельный оркестратор того же запуска блокируется; живой worker повторно не запускается. Внешнее изменение candidate HEAD/файлов останавливает продолжение. Git-коммит имеет сохранённое намерение и восстанавливается после аварии между commit и ledger checkpoint.

После обычного истечения окна: `resume`. После неуспешного или неопределённого вызова обычный resume сначала пытается восстановить ответ. Если повтор действительно нужен, используйте:

```sh
codex-arena resume /path/to/project --retry-interrupted
```

Этот флаг явно разрешает повторные затраты, максимум `max_attempts` на задание. Для оборванного редактора полный неигнорируемый dirty tree сначала сохраняется в отдельную `arena/<run>/recovery-*` ветку, затем **только его Arena worktree** возвращается к последнему checkpoint и редактор запускается повторно. Игнорируемые файлы в Git backup не попадают. Изменённую Git-историю автоматически не сбрасываем.

Порог планирования: soft 15 млн, emergency 17 млн; перед волной резервируется `job_reserve_tokens × число вызовов`. 8–12 млн — ориентир пользователя, а не измеренный прогноз. При необходимости можно явно поднять soft до сохранённого emergency:

```sh
codex-arena resume /path/to/project --soft-tokens 17000000
```

Raw = input + output; cached — часть input, выводится отдельно. Reasoning не складывается повторно с output. Токены не конвертируются в процент/остаток лимита подписки. Жёсткий потолок не гарантируется: usage приходит после вызова, один turn может превысить резерв. Wall-time ограничивает dispatch; текущий вызов дополнительно ограничен job_timeout.

Неизвестный расход блокирует следующие вызовы, включая retry. Сначала сверяйте JSONL/историю Codex, затем явно внесите подтверждённые значения (не подставляйте нули, чтобы обойти бюджет):

```sh
codex-arena reconcile-usage /path/to/project --attempt /absolute/path/0001.envelope.json --input-tokens 12345 --output-tokens 678 --cached-input-tokens 10000
codex-arena resume /path/to/project --retry-interrupted
```

При безвозвратно потерянном usage точное автоматическое продолжение небезопасно; инструмент сохраняет паузу. Политики exactly-once и точного server-side token cap CLI не предоставляет. Если процесс Codex пережил аварийное завершение оркестратора, дождитесь его выхода и повторите resume. Не завершайте PID без проверки его идентичности.

## Итог

`ready` означает: обязательные внешние команды прошли, запрещённых изменений нет, финальный аудитор не сообщил блокеров. Это не доказательство отсутствия всех ошибок. `winner_branch` заполняется только для ready. Для остальных состояний доступны все candidate/recovery-ветки и причины остановки; если чемпион уже выбран, он есть в `candidate_for_review` и diff.

Отчёты содержат исходную базу, SHA/ветку победителя, все находки и review-статусы, baseline/final проверки, причины остановки, usage и журналы. `verified_fixed` — заключение независимого модельного аудитора с evidence, **не автоматическое исполнение каждого reproducer**. До этого находки остаются unconfirmed. Не выдавайте количество сырых пунктов за число уникальных подтверждённых багов.

Benchmarks подключаются как внешние проверки: команда должна сама проводить повторные измерения, учитывать шум и возвращать ненулевой код при недопустимой регрессии. Логи и длительности сохраняются; собственного статистического движка в v0.1 нет. Smoke/browser-команды должны самостоятельно дождаться готовности своего сервера и завершиться; оставшаяся группа процессов останавливается runner.

## AI Factory

Подготовлен `examples/ai-factory-task.md`: сценарии навигации, задания, вложения, библиотека, темы, адаптивность, сохранение данных, честные mock-состояния и сохранение визуального направления. Это отдельный профиль задачи, ядро не зависит от AI Factory.

Текущая папка ChatGPT-проекта и `prototype-2026-10-13` не являются подготовленным Git-репозиторием для турнира. Существующий прототип — статические HTML/CSS/JS; профиль `web-app.toml` для npm **не подходит к нему без адаптации**. Перед реальным прогоном нужно подготовить отдельный Git checkout прототипа и внешние браузерные проверки реальных сценариев; исходные synced files не менять. Этот шаг и реальный прогон пока не выполнялись.

## Ограничения первой версии

- macOS/Linux; доверенный локальный репозиторий. Worktrees и подсказки не заменяют OS sandbox/container. Возможности MCP/hooks/user config наследуются от Codex; их нужно учитывать перед реальным запуском. Bypass sandbox не применяется.
- Нет автоматической переоценки severity/доказанного воспроизведения каждого finding; итоговая независимая проверка модельная плюс фиксированные внешние gates.
- Если оба кандидата провалили gates или финальный аудит нашёл блокер, автоматического repair-round нет: результат сохраняется для рассмотрения.
- Существующие тесты/config защищены консервативно; некоторые полезные рефакторинги потребуют отдельного решения.
- Resume может повторить оборванные **внешние проверки**, но не завершённые модельные задания.
- Полный запуск через реальный Codex ещё не проверен. Автоматические интеграционные тесты используют fake executable на границе модели, реальные Git worktrees, SQLite и реальные проверяющие процессы.
